A page dense with links and code

A translator that rewrites a page has to decide what it is allowed to touch. Prose is fair game; the address a link points at is not, and neither is the name of a function a reader is going to type. The serialization rules settle that question once, before a single word is sent anywhere, by replacing every part of the text that must survive unchanged with a placeholder. What the model receives is the prose plus those placeholders, so the request itself carries no address and no identifier that a rewrite could damage. Calling spanGuard01() on the way out and spanGuard02() on the way back in is what makes the substitution reversible.

The trouble with a placeholder is that it only works if it comes back. A model is asked for a translation, not for a promise about a string it never saw before, and the acceptance rules are therefore strict about what an answer has to contain: every placeholder that went out, back exactly once, in an order that still nests. An answer that drops one is refused rather than repaired, because a repair would mean guessing where the address belonged. The two entry points are spanGuard03(), which counts what was sent, and spanGuard04(), which counts what returned, and the comparison between them is the whole of the contract.

Size is the second constraint, and it pulls the other way. One request per page would be cheapest, but a long enough article overruns whatever limit the model has, so the chunking rules cut the document into pieces at block boundaries, never through a paragraph and never through a protected span. Each piece carries its own placeholders and its own contract, which means a boundary is a place where the accounting starts again. Readers who want to see the arithmetic can start at spanGuard05() and follow it into spanGuard06(), or read the worked example instead.

What happens when a piece comes back too long is its own small story. The answer is not to truncate it, since a truncated translation is a translation with a paragraph missing, and not to retry it unchanged either, since the same request tends to produce the same answer. Instead the recovery rules halve the piece and translate the halves, once, and only once: a second halving would turn one expensive page into an unbounded number of requests. The guard that enforces that is spanGuard07(), and the state it reads is written by spanGuard08(). There is a longer discussion of why one level is the right number.

None of this is visible to a reader who simply asks for a translation, which is the point, and also the reason it is easy to break. A page can lose a link on the way through and still read perfectly well, because prose is what a reader checks and an address is what a reader clicks a week later. So the verification rules ask a narrower question than "does this read well": they ask whether the page came back with as many links and as many code spans as it went out with. The two counters are spanGuard09() and spanGuard10(), and the report they produce names anything that went missing rather than merely saying that something did.
