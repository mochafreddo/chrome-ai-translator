# Leave the Semantic Block session cap to the content script

Status: accepted

Inline Translation refuses to spend more than 60,000 characters of Semantic Block cost on one reading session. That rule lived twice. The content script enforces it: `takeInlineViewportBlockBatch` refuses a block whose reserved cost would push `store.sessionRecordCost` past `INLINE_BLOCK_SESSION_MAX_CHARS`, marks it `failed` with `session_too_large`, files a `runtime.session_too_large` diagnostic, and the Inline Translation Section tells the reader the session reached its limit and no request was sent. The service worker held a second copy — `assertInlineBlockSessionBudget` and `INLINE_BLOCK_MAX_SESSION_COST` — which was exported and unit-tested and called by nothing. The worker copy is now removed; the session cap belongs to the content script alone.

The worker copy read as defence in depth, but there is no second party for it to defend against. The manifest declares no `externally_connectable`, so no web page can send a runtime message to the worker; the only sender of `TRANSLATE_VISIBLE_BLOCK_BATCH` is our own content script. What the worker copy would actually have guarded is our own accounting going wrong — worth something, but not what it looked like.

Enforcing it worker-side was the other available answer, and it was rejected on cost. The worker has `stateByTab` and `activeTranslationsByTab`, and the batch handler has `sender.tab.id` and the `operationId`, so an accumulator is reachable. What is not reachable is the *session*: it resets when the reader presses **Original text** and is carried forward when they restart from stopped, and the worker is told about neither. Enforcing worker-side therefore means inventing a session lifecycle across the seam and keeping two copies of it in step — more coupling and more state than the accounting slip it would catch.

## Consequences

- The worker still enforces the per-batch cap (`INLINE_BLOCK_MAX_BATCH_COST`), the per-record cap (`INLINE_BLOCK_MAX_RECORD_COST`), and the record count (`INLINE_MAX_RECORDS`). Only the session cap is one-sided, and deliberately so.
- `INLINE_BLOCK_SESSION_MAX_CHARS` in `extension/content.js` is the only declaration of *this rule's* 60,000. The number appears once more, as `limits.maxSessionCost` in `extension/inline-diagnostics-protocol.js` — that one bounds how much diagnostic evidence one payload may carry, and shares nothing with the session cap but its digits and an unhelpfully similar name. Do not consolidate the two.
- The batch and record caps are still declared twice each — `INLINE_BLOCK_BATCH_MAX_CHARS` against `INLINE_BLOCK_MAX_BATCH_COST`, and `INLINE_MAX_RECORDS` under that one name on both sides — and nothing keeps either pair in step. Both were left alone because each backs a rule both sides actually run, so both copies do work. That is the test for whether a duplicated constant may stay.
- If the content script's session accounting is wrong, nothing downstream refuses the traffic. `store.sessionRecordCost` is carried across restore and restart by hand, so that accounting is now the only thing standing between a slip and the reader's OpenAI credit. Treat changes to it accordingly.

## Do not revert this

Re-adding a session assert to the worker looks like cheap insurance — a few lines, a green test, nothing to coordinate. It is neither cheap nor insurance. Without a session lifecycle it has no correct value to compare against: a per-tab accumulator that never learns about **Original text** starts refusing blocks in a session the reader has already reset, and one that never learns about restart-from-stopped forgets cost the page is still counting. Either way the reader sees traffic refused for a budget nobody can point at.

This is the failure ADR-0002 describes, one layer up. The uncalled assert survived because a passing unit test named it, which is indistinguishable from the check being live. `tests/background-helpers.test.js` now enumerates both retired names and reads the worker's source for them, so re-adding either — exported or not — fails loudly instead of sitting in the tree. Like ADR-0002's retired message names, that list generalises no further than what it names: a session cap under a third name would pass it. If the session cap is ever genuinely wanted worker-side, build the lifecycle first and make the test that fails when its caller disappears.
