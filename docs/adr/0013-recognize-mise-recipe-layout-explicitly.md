# Recognize the mise recipe layout as an explicit site boundary

Status: accepted

The mise home page's recipe list places a step label, independent heading and paragraph in one DIV beside a second DIV containing terminal commands and output. The latter uses DIV and SPAN rather than PRE or CODE, so its DOM does not establish a general code boundary. Inline Translation recognizes the observed recipe structure specifically on the mise home page, translates the explanatory container's own prose under the LI's ownership, and preserves the code container. The [design interview](../design/mise-sibling-containers-2026-11-01.md) records the confirmed scope, boundaries and verification plan; the [architecture reference](../architecture.md#dom-boundaries) describes the current implementation.

Admission requires `LI.recipe-row` with `DIV.recipe-text` followed by `DIV.recipe-code.terminal-lines`, with only whitespace outside those two elements. The prose DIV retains ADR-0012's attribute restrictions. The code DIV's contents are limited to the observed DIV, SPAN and text structure; interactive or editable contents are refused. Other sites and layouts retain their existing classification. This is an explicit interpretation of the site's recipe layout, not an inference that arbitrary DIV text is code.

The code container keeps its identity and position and is excluded from the parent's translated prose. Its command and output text can change without invalidating the parent's translation or restoration while that container and the admitted boundary remain valid. Applying or restoring rechecks the boundary and refuses replaced or moved containers. Neither operation restores an older code subtree. Headings and paragraphs retain their independent Semantic Block ownership.

This supplements [ADR-0012](0012-translate-through-a-sole-generic-div-wrapper.md) with an explicit site-specific exception. Treating arbitrary sibling DIVs as Block Children was rejected because it could silently exclude ordinary prose from translation. General DIV block inference and command/output heuristics would broaden the design beyond the observed layout. The selected boundary depends on the site's markup and does not make those classes a code signal on other sites. Existing Semantic Block and Block Child vocabulary remains sufficient; no site-plugin framework is introduced.
