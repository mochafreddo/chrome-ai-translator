## Confirmed objective and content

Translation accuracy and structural preservation are mandatory acceptance conditions. Among candidates that satisfy them, the objective is to reduce the time until validated translation is displayed. Tokens per second and time to first token are supporting measurements rather than the final selection criteria.

The first comparison covers English-to-Korean technical documentation, GitHub content, and general articles. Inline Translation and Side Panel Translation are evaluated separately because their work units, display timing, and failure boundaries differ. The existing [glossary](../../GLOSSARY.md) defines those experiences; this discussion introduces no new domain term.

## Confirmed initial comparison and cost decision

The initial experiment keeps the current model, prompt, reasoning setting, recovery limits, and privacy conditions fixed, comparing default provider routing with throughput-first provider routing. OpenRouter selects eligible providers under each policy; this does not pin individual providers. Model changes and Auto Router are deferred to later comparisons if this experiment leaves a measured need. Confirmation of the comparison does not select a production routing policy.

The comparison measures completion-time distributions and cost per successful page, including repair requests, before choosing an acceptable cost increase. Median and p95 completion times are intended measurements, but an initial small sample cannot establish reliable tail latency. A total spending budget must be agreed before billed execution; deferring the production cost threshold does not authorize uncapped spending.

## Confirmed pilot and quality assessment

The pilot uses one page from each confirmed content category: three pages, two translation experiences, two routing policies, and three repetitions of each combination, for 36 page translations. Chunking, batching, and repair can produce more than 36 API requests. Routing execution order alternates to reduce time-order bias, and repeated page translations must not reuse the extension's translated-output cache. Provider prompt-cache effects, if observable, are reported rather than assumed absent. This exploratory sample does not support a reliable p95 conclusion.

Quality assessment combines the existing structural validators with source-to-translation review. Review copies conceal the routing policy, while a separate mapping preserves the association for analysis. Review checks omissions, meaning changes, terminology, and style consistency; a material quality regression blocks adoption even if completion time improves. Structural pass counts alone do not establish semantic accuracy. Repair frequency and final failures are reported alongside accepted results; failed attempts remain part of the experiment's cost.

## Authorized live comparison

After preparation, the user authorized implementing and verifying spending controls and executing the fixed pilot with USD 2 of model spend. Existing OpenRouter authentication is used through the dedicated key-handling module; credentials are not printed, exported, rotated or reconfigured. This supersedes the preparation-only restriction for this live pilot, without authorizing product routing changes, commits or publication.

Both routing arms apply identical `provider.max_price` caps of USD 0.33 per million input tokens, USD 1.32 per million output tokens, and USD 0 per request. The provider inventory omits request-price fields; it does not measure zero request charges. The explicit zero request-price constraint supplies that boundary. These ceilings do not exclude any input/output rate in the inspected inventory, but can exclude future or additional pricing dimensions. The comparison is default versus throughput routing under the same price ceilings.

Before each actual POST, one shared synchronous ledger reserves the full maximum model context's input cost plus the request's output-token cap. The live entry reads the current public endpoint inventory and refuses unknown or larger-than-supported context bounds. Settlement rounds actual costs upward to nanodollars. Unknown cost retains the full reservation and freezes further dispatch; a bill above its reservation is recorded and freezes further dispatch. Service enforcement of the price and output caps, model context bound, and documented inference billing remains an external assumption. The USD 2 model-spend scope excludes credit-purchase fees and taxes; no credits are purchased by the pilot.

The actual key remains inside a fixed-host Node transport callback. The disposable browser always stores a synthetic key. Intercepted requests are validated and reserved, sent through the bounded transport, and their responses are fulfilled back into the browser. A replacement worker therefore cannot obtain the actual key or bypass paid dispatch through the ledger. Real Responses calls and metadata reads target only the fixed OpenRouter hosts and API paths. The bound transport becomes unusable after its callback ends.

The browser receives the response before generation-metadata lookup finishes. Metadata lookup and settlement complete before advancing to the next page; unconfirmed in-flight costs halt the pilot and retain reservations. A timeout or failure cannot quietly transfer late requests to a later run. Evidence-write failures do not skip browser cleanup. The shared browser path is exercised with synthetic responses and synthetic ledger costs before live execution; those synthetic costs remain distinct from actual billing.

This controlled Node relay adds driver and HTTP-client overhead to both arms. Completion time is measured at the extension display boundary, not at raw provider time-to-first-token or screen-paint time. Results therefore describe this controlled pilot rather than a direct measurement of the unmodified browser transport. Quality review is blinded to routing and remains separate from structural completion. A failed arm's incomplete initial coverage is reported as a comparability limitation while its costs and failures remain reportable.

The authorized live pilot completed all 36 runs with USD 0.072118448 of reported model spend and no unsettled reservations. ### Exact schema constraint

The current [Inline request schema](../../extension/inline-model-execution.js) sets `translations.minItems` and `maxItems` to the input record count. [Anthropic structured-output documentation](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations) permits only `minItems` values zero or one and rejects other array bounds. This is a documented native-schema incompatibility; no evidence was found that OpenRouter makes this exact schema compatible. [Gemini documentation](https://ai.google.dev/gemini-api/docs/structured-output) lists both bounds as supported. [Upstage Responses documentation](https://console.upstage.ai/api/responses) documents JSON Schema output, but explicit support for both bounds remains unverified.

Q12 is proposed: for the experiment only, all five models receive the same strict object/array/string schema with both array-length bounds removed. Required properties and `additionalProperties: false` remain. The current local validator still rejects missing, duplicate or unexpected IDs and non-string templates, and then validates Placeholder Token structure and translation quality. This preserves exact returned-record coverage when input IDs are unique. The existing local parser does not itself reject extra object properties, so a future experiment check must also verify the complete accepted shape rather than claiming that parser alone enforces every JSON Schema rule. Initial and recovery requests must use the same common schema. DeepSeek must be evaluated again with that schema; earlier production-schema results are not a comparable control. Extra errors and their costs remain reportable. This proposal changes neither the product schema nor product routing defaults. Leaving the product schema mandatory would instead require excluding Claude from Inline comparison or limiting it to Side Panel comparison.
