# Charge the Session Budget in actual record cost

Status: accepted

The Session Budget bounds what one Inline Translation Session may spend. It charged each Semantic Block `getInlineBlockReservedRecordCost` — the size of the JSON request that would carry that block *alone*, counted twice, once as sent and once again with the repair field padded to its maximum — against a limit named `INLINE_BLOCK_SESSION_MAX_CHARS = 60000`. It now charges `getInlineBlockRecordCost` — the record's template plus its serialized atoms plus its serialized `repair` field, with no id and no request wrapper — against `INLINE_BLOCK_SESSION_MAX_RECORD_COST = 150000`, plus one further charge of the same amount for a block whose answer needed a repair. `getInlineBlockReservedRecordCost` is unchanged and keeps its job: the per-batch and per-record request-size caps, on both sides of the seam.

The two cost functions answer different questions and were sharing one answer. Reserved cost deliberately over-counts, so that a real batched request can never exceed the cap it was checked against — a guarantee about the size of **one request**, which only the request-size caps need. A cumulative budget needs no such guarantee, and inheriting the over-count made the budget several times tighter than its name said, by a factor that varies with the page's block shape rather than with its length. The fixed per-block wrapper is charged to every block and then charged again, so the shorter the blocks the worse the ratio: a page of table cells and list items pays many times the text it holds, and nobody reading "60,000 characters" could predict when it would fire.

The measurement that settled it. One real page, through a headless browser against the live DOM: `article.markdown-body` on a GitHub repository landing page — 356 Semantic Blocks (91 paragraphs, 29 headings, 23 list items, 213 table cells) holding 37,392 characters, median block length 36 characters, 67.7% of blocks under 100 characters. Reserved cost for that page is roughly 168,000 against a 60,000 budget, so translation stopped about a fifth of the way down. Its actual record cost is roughly 40,000, or roughly 46,000–55,000 once repair charges are estimated in. `tests/content-helpers.test.js` reconstructs that shape as bare records — 356 blocks, 37,376 characters, 39,512 actual against 164,248 reserved — and holds that the whole page is admitted.

A repair is a second real request, not a hypothetical one. When an answer fails validation in a repairable way, `translateVisibleBlockBatch` sends the same record again with a `repair` field and reports `attemptCount: 2` for it. An earlier reading of the reserved cost held that its doubling stood for a request that would never be sent; that was wrong, and it is why this change adds a charge for the repair rather than simply deleting the doubling. A repair is charged the record's own cost again, which is a stated approximation rather than the repair request's exact size: the worker fills in a `repair` field the content script never sees, bounded by the diagnostic code length, so the charge is short by at most a few dozen characters per repaired block. Charging what the content script can actually measure is preferred to modelling the worker's payload from the other side of the seam. The charge attaches in `applyInlineViewportBlockResults`, where a result has come back, and only there: `attemptCount` is written into the translation cache and read back out of it, so a block that needed a repair once presents a 2 again on a later cache hit with nothing sent. Cache hits are charged nothing at all — a cached block is applied before it ever enters the queue — and charging one for last session's repair would be a new bug wearing this fix's clothes.

There is no refund. A charge is never returned: not on a failed request, not on a failed batch, not on a stale response. The set of failures where nothing was demonstrably sent is nearly empty — the worker's only pre-request rejection is a missing API key, which the content script already checks before a run starts — while everything past that point has passed the model call, where billing is unknowable from the outside: a rate-limited request was not billed, a timeout after generation began was. Guessing in the reader's favour would put a hole in the guard; guessing against them would overcharge. Charging once at assembly, and once more when a repair is reported, is the only rule that needs no guess. The content script's own local rejections — a block too large, an unsupported block, the budget exhausted — are refused *before* any charge, so they need no refund and get none.

150,000 answers one question: what value does no ordinary article reach? Under actual-cost charging the measured page costs roughly 46,000–55,000 with repairs, so 60,000 would have admitted it with 10–25% headroom, which is a near miss rather than an answer. 150,000 is roughly three times the longest realistic article, and it admits the measured page even in the impossible case where every one of its blocks needed a repair. Moving the number also has a wanted second effect: `60000` appears in this codebase as four unrelated limits — this rule, the full-page Side Panel Translation total, the maximum configurable Translation Chunk size, and the diagnostics payload's own session bound — with nothing keeping any of them in step and nothing but their digits relating them. ADR-0003 forbids consolidating this rule's number with the diagnostics one; moving to 150,000 makes that consolidation structurally impossible instead of merely forbidden.

The constant is renamed away from `_CHARS` because its unit is record cost and never was characters — the same misreading the reader-facing message just lost. `INLINE_BLOCK_SESSION_MAX_RECORD_COST` matches `getInlineBlockRecordCost` and is deliberately unlike `INLINE_BLOCK_MAX_SESSION_COST`, the retired worker-side name ADR-0003's guard forbids. That guard reads the service worker's source only, so the content script's constant is outside it, but a name that read like the retired one would invite exactly the revert ADR-0003 argues against.

## Consequences

- A repair reported for a record whose operation the page has already replaced is still charged. The charge is taken before `applyInlineViewportBlockResults` decides to ignore the result, because `store.sessionRecordCost` spans the page visit rather than the operation, and the request was sent either way.
- A batch that fails outright is the one repair that goes uncharged, and unavoidably so: `markInlineViewportBatchFailed` has no results, so no `attemptCount`, so nothing says whether a repair was sent. The initial charge stands and nothing is added. This is a bounded under-count of the guard, not a refund.
- The Session Budget can now be exceeded *after* the fact. The repair charge lands when the repair request has already been sent, so the excess is unrefusable; it surfaces only as the next batch being refused. The over-limit state is the accounting working, not the limit check failing.
- Inside the batch-assembly loop the per-batch accumulator uses reserved cost while the session accumulator uses actual cost, on adjacent lines, for the same record. That is deliberate and is the thing this ADR exists to defend. Consolidating them either reintroduces this bug or breaks the guarantee that a real batched request never exceeds the cap it was checked against.
- The reader is told no figure. `getInlineTerminalReason` says the visible translation reached this page visit's limit, that no request was sent, and that reloading the page continues. Naming reload amounts to telling the reader how to spend more, and is deliberate: reload is the re-authorization gesture in this design, and concealing it would leave the reader stuck in service of a guard that does not bound spending anyway.
- The Session Budget is a runaway guard and not a spending ceiling. It bounds one page visit; a reader who reloads three times spends three times as much, by design. No spending ceiling exists in this extension and this change does not add one. Both `CONTEXT.md` entries state it, because that misreading is where this bug started.
- A longer page now meets the Semantic Block record count cap before the Session Budget. The measured page holds 356 blocks against `INLINE_MAX_RECORDS` of 500, and that limit reports a different failure. A reader near it seeing that other message is not this bug returning.
- The accounting is checked as behaviour rather than as arithmetic, in `tests/content-helpers.test.js`: a set of blocks whose reserved cost exceeds the limit and whose actual cost does not is admitted in full; the measured page's shape drains to the end; a record returned with `attemptCount: 2` costs more than the same record returned with 1; a cached block with `attemptCount: 2` costs nothing; a failed batch releases nothing; and the reader's message names no digit. None of it hand-computes a cost function's output, so changing how a record is serialized does not rewrite these checks.
- `attemptCount` is now asserted where it is produced as well as where it is consumed, in `tests/background-helpers.test.js`. Money rests on that field; testing it only at the consumer is the shape of failure ADR-0003 was written about.
- Everything above is browser-free and stays in `npm test`. Nothing here needs a real browser or an API key.

## Do not revert this

Charging reserved cost to the session looks tidier than keeping two costs in one loop, and it is the version that shipped a bug for a month. Reserved cost is a statement about one request: over-count it and the batch you send is guaranteed to fit the cap you checked. Summed over a page it stops being a bound on anything and becomes a per-block tax whose rate is set by the page's block shape, which is why a reader on a table-heavy page lost translation a fifth of the way down while the message named a number they could not count.

Removing the repair charge is the other tempting simplification, and it would be wrong for the opposite reason: the second request is real, it reaches the model, and the reader is billed for it. The `attemptCount === 2` it keys on is an exact match rather than `>= 2`, because the worker sends at most two requests per record; a third attempt would need this charge revisited rather than silently counted as the second, and `tests/background-helpers.test.js` now pins the field where it is produced.

What would justify reopening the number is a real page that reaches 150,000, or a spending ceiling actually being designed. The first is a measurement; the second is a separate feature with its own design, and it does not arrive by widening this guard until it looks like one.
