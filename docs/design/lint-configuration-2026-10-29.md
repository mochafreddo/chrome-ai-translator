# lint 구성 설계 인터뷰

이 문서는 기준 커밋 `1234cb1ccde2dfca6ec30ed59468901951fd1a23`에서 시작한 lint 구성 설계 인터뷰를 기록한다. 2026-10-29에 사용자가 Q1부터 Q8까지 추천안을 모두 수락하고, Q9의 최종 작업·검증 범위 제안에 이어 `implement`를 요청해 개발 패키지 설치, 구현·검증과 현재 브랜치 커밋을 승인했다. 푸시와 배포는 포함하지 않는다.

## 근거와 한계

[패키지 스크립트](../../package.json)에는 lint 명령과 개발 의존성이 없다. [구문 검사](../../scripts/check-syntax.js)는 `extension/` 바로 아래의 일반 `.js` 파일을 Node의 `--check`로 검사한다. [로컬 검증](../../scripts/verify-local.js)은 구문 검사, 문서 검사, 단위 테스트를 실행하고, 결과 재사용 시 개발 의존성과 `node_modules`가 없는 조건을 확인한다. [CI](../../.github/workflows/checks.yml)는 구문 검사, 문서 검사, 단위 테스트와 별도의 브라우저 fixture 검사를 실행한다.

[아키텍처](../architecture.md)의 확장 코드는 classic script로 로드되며, 공유 모듈은 브라우저 전역 API와 보호된 CommonJS export를 함께 제공한다. 테스트와 도구에는 CommonJS `.js`와 ESM `.mjs`가 함께 있다. 따라서 실행 환경별 전역 변수와 소스 형식을 구분해야 한다. 이 조사는 파일을 읽어 확인한 결과이며 lint 위반 수, 실행 시간, 테스트 통과 여부를 측정한 결과는 아니다.

## 합의한 결정

### Q1: 오류 탐지에 집중

lint는 미정의 변수, 잘못된 조건식, 사용하지 않는 변수 등 오류 가능성을 탐지하는 데 집중한다. 들여쓰기, 따옴표, 줄 길이는 강제하지 않는다. 기존 서식을 유지하고 formatter 도입은 이번 범위에서 제외한다.

### Q2: 개발 의존성 허용

lint 도구를 개발 의존성으로 추가하고 lockfile로 버전을 고정한다. 로컬과 CI가 저장소에 고정한 도구를 사용한다. 이에 맞춰 로컬 검증 기록 재사용 조건도 설계한다. 확장 프로그램의 빌드 과정은 추가하지 않는다.

### Q3: JavaScript 검사 범위

`extension/`, `scripts/`, `tests/`의 JavaScript를 검사한다. 브라우저, worker, Node 실행 환경을 구분한다. HTML, CSS, Markdown lint는 이번 범위에서 제외한다.

### Q4: ESLint flat config

ESLint의 flat config를 사용하고 파일별로 classic script, CommonJS, ESM과 전역 변수를 구분한다. 기존 로딩 구조를 유지하며 브라우저와 Node 전역을 모든 파일에 일괄 허용하지 않는다.

### Q5: recommended 규칙을 출발점으로 사용

ESLint의 `recommended`를 기본으로 삼고 실제 코드에서 오탐이 확인된 규칙만 근거를 남겨 조정한다. 별도 플러그인, 복잡도, 함수 길이, 명명 규칙은 처음부터 추가하지 않는다. 기존의 보호된 CommonJS export를 정상 패턴으로 인정한다.

### Q6: 기존 위반 정리

도입 완료 시 검사 대상 전체가 통과하도록 기존 위반을 정리한다. 기존 위반을 일괄 무시하는 baseline은 만들지 않는다. 동작을 보존하는 수정은 포함하고 동작 변경이 필요한 발견은 따로 설명해 결정한다. 현재 위반 수는 측정하지 않았다.

### Q7: 로컬 검증과 CI 연결

`npm run lint`를 만들고 로컬 전체 검증과 CI에 포함한다. 기존 구문 검사를 유지한다. lint는 파일을 변경하지 않고 위반이 있으면 실패한다. 자동 수정과 Git hook 추가는 제외한다.

### Q8: 설치된 의존성까지 비교해 검증 결과 재사용

소스, 설정, lockfile과 실제 설치된 의존성 파일을 검증 전후 및 재사용 시 비교한다. 의존성 파일의 추가, 삭제, 수정과 연결 대상 변경을 감지한다. 같은 lockfile 아래에서 설치 파일만 바뀌어도 재사용을 거절하는 테스트를 둔다. 기존 로그 무결성, 실행 조건과 검사 중 입력 변경 감지는 유지한다. lockfile만으로 설치된 코드가 같다고 판정하지 않는다.

## Q9: 확정한 작업·검증 범위

구현과 검토는 아래 범위를 따른다. `implement`의 절차에 따라 두 축의 코드 검토와 최종 검증 후 현재 브랜치에 커밋한다.

| 저장소 | 작업 범위 | 공개 테스트 경계 | 검토 기준 |
| --- | --- | --- | --- |
| chrome-ai-translator | Q1~Q8의 ESLint 설정과 개발 의존성·lockfile, 검사 명령, 기존 위반의 동작 보존 수정, 로컬 검증·CI 연결, 설치된 의존성 비교, 관련 테스트·사용 안내·에이전트 안내의 갱신 | lint CLI의 진단·종료 코드·파일 비변경, 실행 환경별 정상 코드 수용과 잘못된 전역 참조 거절, 검증 CLI의 기록 생성·재사용·변경 거절 | `1234cb1ccde2dfca6ec30ed59468901951fd1a23` 대비 이 인터뷰에서 합의한 변경과 작업 트리 |

개발 패키지는 적용 시점의 공식 지원 조건과 로컬·CI Node 버전을 확인한 뒤 고정한다. 설치된 의존성의 파일 목록·내용·모드·연결 대상과 검사 중 변경을 확인하며, 일반적인 패키지 설치가 만드는 저장소 내부 연결은 비교 대상에 포함한다. 저장소 외부의 의존성 연결이나 지원 범위 밖의 실행 조건은 재사용을 거절한다. 기존 비밀 파일 제외와 무관한 미추적·무시 파일의 재사용 거절을 유지하고, 의존성 디렉터리만 명시적인 수집 대상으로 구분한다. 의존성 파일의 원문은 기록에 저장하지 않는다.

검증은 실제 lint CLI를 통과하는 정상 사례와 미정의 변수 등을 거절하는 실패 사례, 실행 환경별 설정 사례, 재사용 CLI를 통한 입력 변경 거절 사례를 기존 테스트 방식에 추가한다. 의존성 코드 변경, 파일 추가·삭제, 연결 대상 변경, 검사 중 변경과 로그 변조에 대한 거절을 확인한다. 테스트의 정답은 합의한 계약에서 정하고, 고친 로직을 되돌리면 회귀 검사가 실패하는 대조군도 확인한다. 소스 변경을 사용하는 대조군은 공통 mutation-probe 절차를 따른다.

검토와 필요한 수정 후 입력을 고정하고 `npm run verify:local`로 lint, 구문 검사, 문서 검사, 단위 테스트를 검증한다. 이어 같은 기록의 재사용 성공과 관련 변경의 재사용 거절을 확인한다. 제품 소스 수정은 동작 보존 범위로 제한하며, 동작 변경이 필요하면 별도 결정으로 다룬다. 브라우저 검사와 과금 모델 검사는 기본 범위에서 제외하고, 실제 수정에서 브라우저 동작에 대한 불확실성이 생기면 해당 경로의 비과금 검사 필요성을 재평가한다. CI 정의와 로컬 검증만으로 원격 CI 통과를 주장하지 않는다.

## 문서화 경계

새 제품 도메인 개념은 없으므로 용어집은 변경하지 않는다. lint 도구와 규칙은 되돌리기 쉬운 개발 설정이므로 별도 ADR을 만들지 않는다. 채택 이유와 검증 경계는 이 기록에 남긴다. 합의 기록은 실제 검사 결과나 원격 CI 통과 증거로 취급하지 않는다.
