# Leave the Semantic Block session cap to the content script

Status: accepted

Inline Translation refuses to spend more than a fixed amount of Semantic Block record cost on one Inline Translation Session. That rule lived twice. The content script enforces it: `takeInlineViewportBlockBatch` refuses a block whose cost would push `store.sessionRecordCost` past `INLINE_BLOCK_SESSION_MAX_RECORD_COST`, marks it `failed` with `session_too_large`, files a `runtime.session_too_large` diagnostic, and the Inline Translation Section tells the reader the visible translation reached this page visit's limit and no request was sent. The unit and the value are ADR-0007's subject, not this one's; when this ADR was written the constant was `INLINE_BLOCK_SESSION_MAX_CHARS` and the cap was 60,000 of reserved cost. The service worker held a second copy — `assertInlineBlockSessionBudget` and `INLINE_BLOCK_MAX_SESSION_COST` — which was exported and unit-tested and called by nothing. The worker copy is now removed; the session cap belongs to the content script alone.

The worker copy read as defence in depth, but there is no second party for it to defend against. The manifest declares no `externally_connectable`, so no web page can send a runtime message to the worker; the only sender of `TRANSLATE_VISIBLE_BLOCK_BATCH` is our own content script. What the worker copy would actually have guarded is our own accounting going wrong — worth something, but not what it looked like.

Enforcing it worker-side was the other available answer, and it was rejected on cost. The worker has `stateByTab` and `activeTranslationsByTab`, and the batch handler has `sender.tab.id` and the `operationId`, so an accumulator is reachable. What is not reachable is the *session*: it survives **Original text** and it survives restart-from-stopped, both of which carry the spent amount forward, and it ends only when the page is reloaded or left. Nothing in the seam tells the worker where those boundaries fall. Enforcing worker-side therefore means inventing a session lifecycle across the seam and keeping two copies of it in step — more coupling and more state than the accounting slip it would catch.

This ADR as first written claimed the opposite — that **Original text** resets the Session Budget. It was wrong the day it was written: `16f577c` (2026-07-10) carried the spent amount forward across restore a month before this ADR landed on 2026-08-13, and a check in `tests/content-helpers.test.js` has named that half ever since. The boundary above is a factual correction to that claim, not a record of the behaviour moving.

## Consequences

- The worker still enforces the per-batch cap (`INLINE_BLOCK_MAX_BATCH_COST`), the per-record cap (`INLINE_BLOCK_MAX_RECORD_COST`), and the record count (`INLINE_MAX_RECORDS`). Only the session cap is one-sided, and deliberately so.
- `INLINE_BLOCK_SESSION_MAX_RECORD_COST` in `extension/content.js` is the only declaration of *this rule's* limit. It shared its digits with three unrelated 60,000s when this was written — `limits.maxSessionCost` in `extension/inline-diagnostics-protocol.js`, which bounds how much diagnostic evidence one payload may carry, plus the full-page total and the maximum chunk size in the worker — and shared nothing else with any of them. Do not consolidate them. ADR-0007 moved this rule's number to 150,000, which makes the mistake harder to make by accident but no less wrong.
- The batch and record caps are still declared twice each — `INLINE_BLOCK_BATCH_MAX_CHARS` against `INLINE_BLOCK_MAX_BATCH_COST`, and `INLINE_MAX_RECORDS` under that one name on both sides — and nothing keeps either pair in step. Both were left alone because each backs a rule both sides actually run, so both copies do work. That is the test for whether a duplicated constant may stay.
- If the content script's session accounting is wrong, nothing downstream refuses the traffic. `store.sessionRecordCost` is carried across restore and restart by hand, so that accounting is the only guard between an accounting slip on one page visit and the reader's OpenAI account. It is a runaway guard and not a spending ceiling — a reader who reloads pays again, by design, and no ceiling on that exists — so treat changes to it as changes to a guard, not to a budget the reader was promised.

## Do not revert this

Re-adding a session assert to the worker looks like cheap insurance — a few lines, a green test, nothing to coordinate. It is neither cheap nor insurance. Without a session lifecycle it has no correct value to compare against: a per-tab accumulator that never learns where an Inline Translation Session ends keeps refusing blocks against cost spent before a reload the reader has already performed, and one that resets on whatever tab event it can see instead forgets cost the page is still counting. Either way the reader sees traffic refused for a budget nobody can point at.

This is the failure ADR-0002 describes, one layer up. The uncalled assert survived because a passing unit test named it, which is indistinguishable from the check being live. `tests/background-helpers.test.js` guarded against its return by reading the worker's own source text for the two retired names, and that guard generalised no further than what it named: a session cap under a third name would have passed it. Since #46 the worker is built rather than found — it takes the platform it runs on as an argument — so the guard is an assertion about behaviour instead. One worker translates six Semantic Block batches costing more than the retired cap together, and every one of them has to be applied. A session cap re-added worker-side fails it under any name, whether it is a module constant, an instance's own accounting, or exported at all. If the session cap is ever genuinely wanted worker-side, build the lifecycle first and make the test that fails when its caller disappears.
